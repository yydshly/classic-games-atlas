## 确认的界面问题

本轮修改前普通UI，1440×1000与390×844各15个观察点：尚未结识伙伴，以及已换队但尚待成长时，出行/相遇中的顶部都写“先回营，再一起准备”。这是终挑战准备函数在非营地的统一拒绝理由，被直接拿作旅途当前目标；任务本身可以正常完成，不是卡关或判定错误。

伙伴已答应同行但尚未入册时，回营方向本来正确；本轮让提示明确“带某位伙伴回营入册”，不提前勾选已结识。营地原提示正确，保留。调整队伍尚未完成时出行，也仍应回营调整，不把所有回营提示当错。

## 步骤与验证健康状态

1. **已验：寻找伙伴。**营地提示不变；出行指向原有晶芽草间/回声浅湾，相遇提示羽结结识后带回营。
2. **已验：待入册。**普通羽结招募后点名带新伙伴回营；第一里程碑仍未勾选。直接刷新保持该提示和原状态。
3. **已验：调整队伍/待成长。**回营后原规则入册，调整队伍；营地与出行/相遇均指出两次有结果相遇获得一次成长。成长前刷新保持。
4. **已验：成长与准备。**普通切磋后成长，提示回营可挑战；回营后准备文字不变，再刷新精确保持。开始终挑战原预告不变，主动回营再准备。
5. **仅离线模型已验：已完成目标。**用已有两套合法模型策略生成结局，断言结局/回营/自由出行的完成提示保持原文。没有在浏览器注入完成档，也没有重新进行完整结局UI。

本地每视口24个记录动作、15个观察点、3次精确刷新；使用已知路线与策略的普通按钮，不声称玩家无辅助理解。修改前后30份完整观察状态及命令逐项完全一致，含随机结果、背包、成长、里程碑和回营结果。公开JSON保留观察字段子集及完整origin/commands供模型重放；原始完整截图/报告留在私有测试目录。

10组模型测试验证只读提示、原判定/重放不变、营地/终挑战原文、待入册不冒记完成、未调整队伍回营、单个出行位仍按原规则要求两位，以及两种已完成模型状态。`node docs/feather-objective-qa/test-objective.mjs`。浏览器脚本需环境已有Playwright：`python docs/feather-objective-qa/verify_browser.py --root http://127.0.0.1:静态端口/`；发布后用`--online`。脚本不会安装依赖。线上实测结果与最终SHA在交付记录中另列，不以本地充线上。
